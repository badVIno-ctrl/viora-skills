# Как прислать правку

Спасибо, что хочешь улучшить скилл. Правила простые и их мало.

## Перед первым коммитом

```bash
git clone https://github.com/OWNER/channel-skill.git
cd channel-skill/channel-skill
bash tools/check_all.sh
```

Ответ должен быть одной строкой: всё чисто. Если уже на старте не чисто, открой issue:
значит, проблема не в твоей правке.

## Главное правило стиля

Длинное тире вне закона во всех файлах: в коде, в документации, в примерах, в описании
issue и pull request. Вместо него: дефис, точка, двоеточие. Проверка ловит нарушения автоматически.

Остальное по тексту: короткие фразы, без канцелярита, без штампов вроде «в современном мире».
Файлы скилла пишутся на русском: это инструкции для модели, а не интерфейс.

## Что важно соблюдать

1. Без новых зависимостей в ядре. Только стандартная библиотека python3.
2. Без жёстко вписанных имён каналов, ссылок и цифр. Всё такое берётся из профиля.
3. Новое поведение закрывается самотестом в том же скрипте.
4. Промпты не правятся руками: правишь источник и запускаешь сборку.
5. Секретов в коммитах не бывает. Даже тестовых.

## После правки

```bash
cd channel-skill
python3 tools/build_prompt.py          # если менял блоки CORE
python3 tools/sizes.py --write         # если менял размеры файлов
bash tools/check_all.sh                # всё сразу
```

Точечные команды, если нужно быстро:

```bash
python3 tools/lint_post.py --selftest
python3 tools/validate_skill.py --root ..
python3 tools/run_evals.py
```

## Что менять где

| Задача | Файл |
| --- | --- |
| Новое правило письма | нужный файл в папке reference, плюс строка в `ROUTER.md` |
| Новая рубрика по умолчанию | `tools/profile.py`, блок с рубриками |
| Новый вопрос интервью | `tools/onboard.py`, плюс `ONBOARDING.md` |
| Новая проверка текста | `tools/lint_post.py` или `tools/lint_article.py` |
| Новый эталон поведения | `evals/cases.json` |
| Документация для людей | папка docs в корне |

## Pull request

В описании достаточно четырёх строк:

- что поменялось;
- зачем;
- что запускал и что ответила проверка;
- ломает ли старые профили.

Коммиты лучше писать глаголом и по делу: «добавил вопрос про табу», «починил разрез длинных постов».
Версию и журнал изменений поднимает мейнтейнер при выпуске, в PR это делать не нужно.

## Что точно примут с радостью

- шаблоны профилей для новых ниш и языков;
- новые проверки на ИИ-признаки в тексте;
- переводы документации в папке docs;
- упрощения: меньше файлов и меньше шагов при том же результате.

## Что скорее отклонят

- режимы автоматической публикации без подтверждения человеком;
- сбор статистики и телеметрия;
- парсинг чужих каналов и массовые рассылки;
- скрипты, которые нельзя запустить без платного ключа.
