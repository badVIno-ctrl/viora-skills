# OWASP Top 10:2025 — working reference

For each category: what it actually means, the questions that find it, and the controls that close
it. Use this for a systematic sweep; use `SKILL.md` §5 before reporting anything you find here.

---

## A01:2025 — Broken Access Control

*The single most common source of real breaches. Almost never detectable by regex — the bug is
usually **missing** code.*

**Find it by asking:**
- For every route that reads or writes an object: is there a check that *this user owns this object*,
  not merely that the user is logged in?
- Are object IDs sequential/guessable? Can I change `/api/orders/1042` to `/1043`?
- Is authorization enforced server-side, or does the UI just hide the button?
- Are admin routes protected by a real check or by an unlinked URL?
- Can a role be escalated through a mass-assignable field (`role`, `isAdmin`, `plan`, `tenantId`)?
- In a multi-tenant app: is `tenant_id` in the WHERE clause of *every* query, enforced centrally?
- Does the API return more fields than the UI shows? (Excessive data exposure is access control.)
- Are JWT claims used for authorization re-validated server-side, or trusted as sent?
- CORS: does an over-permissive policy let another origin read authenticated responses?

**Controls:** deny by default · centralised policy layer (middleware/guard/policy object), never
per-handler copy-paste · ownership check bound to the query, not bolted on after · opaque IDs
(UUIDv4/ULID) · explicit field allowlists on input **and** output · row-level security where the DB
supports it · log every denial.

**ASVS 5.0:** 1.2.1–1.2.5 (enforcement point), 1.3.2 (deny by default), 8.2.1–8.2.2 (data-level).

## A02:2025 — Security Misconfiguration

**Find it by asking:**
- Debug mode, stack traces, directory listing, source maps in production?
- Default credentials, sample apps, admin consoles, `/actuator`, `/debug`, `/.git` reachable?
- Security headers present (CSP, HSTS, nosniff, frame-ancestors, Referrer-Policy)?
- CORS: wildcard origin, reflected origin, `credentials: true` with a loose allowlist?
- Cloud storage buckets, databases, caches (Redis/Elastic/Mongo) exposed to the internet?
- Are security flags **default-on**? An unset environment variable must mean *enforced*, not *off*.
- Are `.env`, backups, dumps or `.map` files served or committed?

**Controls:** hardened baseline image/config · config as code, reviewed · environment parity ·
no default accounts · `viora headers` in CI against staging · automated drift detection.

**ASVS 5.0:** 14.2.1 (secure defaults), 12.1.1 (config management).

## A03:2025 — Software Supply Chain Failures

*New in 2025 and rising fast: the attacker doesn't breach you, they breach something you install.*

**Find it by asking:**
- Is there a committed lockfile, and does CI install frozen (`npm ci`, `--frozen-lockfile`,
  `--require-hashes`)?
- Do any packages run install-time scripts (`preinstall`/`install`/`postinstall`)?
- Any dependency pulled from a git URL, tarball URL, or private path instead of the registry?
- Typosquats and slopsquats — including package names *an AI assistant invented*?
- Are CI actions pinned to a commit SHA, images to a digest?
- Do workflows interpolate `github.event.*` into `run:` steps? Does `pull_request_target` check out
  untrusted code? Is `permissions:` scoped?
- Who can publish? Is 2FA enforced on the registry account? Is the publish token in CI only?
- Is there an SBOM and a way to answer "are we affected by CVE-X" in minutes?

**Controls:** frozen installs · `--ignore-scripts` by default with an explicit allowlist · SHA/digest
pinning · dependency review on every bump · SBOM generation · least-privilege CI tokens · separate
build and publish jobs · provenance/attestation where available.

**Triage rule:** a CVE in a dependency is only a finding *for you* if the vulnerable code path is
reachable from your entry points. Reachability first, version number second.

## A04:2025 — Cryptographic Failures

**Find it by asking:**
- Is sensitive data (credentials, tokens, PII, payment, health) encrypted in transit **and** at rest?
- TLS 1.2+ only, valid certificates, verification never disabled?
- Password storage: Argon2id / bcrypt(≥12) / scrypt — never MD5, SHA-1, or unsalted SHA-256?
- Are tokens, session IDs, OTPs, reset links and nonces generated with a CSPRNG?
- AEAD (AES-GCM, ChaCha20-Poly1305) with a fresh random nonce per message — no ECB, no static IV?
- Where do keys live? Are they rotatable? Is the same key used for everything, forever?
- Any home-grown crypto, custom "encryption", or XOR obfuscation?

**Controls:** platform crypto libraries only · KMS/HSM for keys · documented rotation · HSTS ·
encrypt-then-MAC or AEAD · constant-time comparison for secrets.

**ASVS 5.0:** 6.2.1, 6.2.4, 6.3.1 (algorithms and randomness), 11.3.1.

## A05:2025 — Injection

*Includes XSS. If untrusted data reaches an interpreter as syntax rather than as data, it is here.*

**Find it by asking:**
- Any SQL built by concatenation, f-string, `.format()`, template literal or `%s %`?
- Any shell execution with `shell=True`, `os.system`, `exec()`, backticks, or an interpolated string?
- `eval`, `new Function`, `setTimeout("string")`, `Invoke-Expression`, dynamic `import()` of a
  user-controlled path?
- Templates rendered from user-controlled strings (SSTI)?
- Output rendered with escaping bypassed (`dangerouslySetInnerHTML`, `v-html`, `|safe`, `Html.Raw`,
  `innerHTML`)?
- ORM "raw" escape hatches taking interpolated input?
- NoSQL query objects built from raw request bodies (operator injection via `$gt`, `$ne`, `$where`)?
- XML parsing with DTD/external entities enabled?
- Log injection, header injection (CRLF), or email header injection?

**Controls:** parameterised queries everywhere · argv arrays, never shell strings · schema validation
at the boundary (allowlist, typed) · context-correct output encoding · CSP as a second layer ·
`defusedxml` / DTD disabled · reject request keys beginning with `$`.

**ASVS 5.0:** 2.2.1, 2.2.2 (input validation), 7.2.3, 7.2.4, 7.4.1 (output encoding).

## A06:2025 — Insecure Design

*A flaw you cannot patch — you have to redesign. Found by thinking, not scanning.*

**Find it by asking:**
- What is the abuse case for each feature? ("As an attacker I would …")
- Can the business flow be replayed, raced, reordered or skipped? (double-spend, coupon reuse,
  parallel withdrawals, skipping payment step)
- Are limits enforced server-side (quantity, price, quota, rate) or client-side?
- Password reset, email change, MFA enrolment, account recovery — the classic weak links. Are the
  tokens single-use, short-lived, bound to the account, and invalidated on use?
- Is there segmentation between tenants, environments and privilege tiers?
- What happens when a dependency is slow, down or malicious? Does the system fail *closed*?

**Controls:** threat model per feature (see `01-threat-model.md`) · abuse cases as tests ·
idempotency keys · server-authoritative state · defence in depth · secure-by-default library choices.

## A07:2025 — Authentication Failures

**Find it by asking:**
- Rate limiting and lockout on login, registration, password reset, MFA and token endpoints?
- Credential stuffing defences: breached-password check, device/IP anomaly detection, CAPTCHA?
- Session ID regenerated on login and privilege change? Invalidated on logout and password change?
- Session cookies: `HttpOnly`, `Secure`, `SameSite=Lax|Strict`, sensible expiry, scoped path/domain?
- JWT: algorithm pinned (no `none`, no `alg` confusion), signature verified, `exp`/`iss`/`aud`
  checked, revocation possible?
- Is MFA available for privileged accounts, and enforced for admin?
- Do error messages distinguish "user not found" from "wrong password" (enumeration)?
- Are password comparisons constant-time?

**Controls:** proven identity library or provider · Argon2id · strict limiter + backoff · uniform
error messages and response timing · short-lived access tokens + rotating refresh tokens · device
binding for sensitive sessions.

**ASVS 5.0:** 6.x (authentication), 3.x (session management).

## A08:2025 — Software or Data Integrity Failures

**Find it by asking:**
- Any deserialization of untrusted data (`pickle`, `yaml.load`, `ObjectInputStream`, `unserialize`,
  `BinaryFormatter`, `torch.load` without `weights_only=True`)?
- Are updates, plugins, themes or ML models downloaded and executed without signature verification?
- Are webhooks verified by HMAC signature with a constant-time comparison and a replay window?
- Are CDN scripts pinned with Subresource Integrity?
- Is CI able to inject code into a release without review? Who can bypass branch protection?
- Is critical client-side state (price, role, quota) trusted when it returns to the server?

**Controls:** JSON + schema instead of binary deserialization · signature verification before parse ·
SRI on third-party scripts · signed commits/artifacts · protected branches with required review ·
server-authoritative state.

## A09:2025 — Security Logging and Alerting Failures

**Find it by asking:**
- Are login success/failure, authz denial, validation failure, privilege change, admin action, and
  payment events logged with actor, action, target, timestamp and correlation ID?
- Would you *detect* a live credential-stuffing run or a mass data pull today? What alerts fire?
- Are logs tamper-resistant, centralised, and retained long enough to investigate?
- Do logs contain secrets, tokens, full card numbers, passwords or unnecessary PII? (That is itself a
  finding.)
- Is user-controlled data neutralised before being written to logs (log forging / injection)?

**Controls:** structured logging with a redaction filter · append-only sink · alerts on rate
anomalies and privilege changes · an actual runbook for the alert (see `09-checklists.md`).

## A10:2025 — Mishandling of Exceptional Conditions

*New in 2025. Covers fail-open logic, swallowed errors, and information disclosure through errors.*

**Find it by asking:**
- Does any security decision return "allow" on exception, timeout or missing config? (Law 4)
- Are exceptions swallowed (`except: pass`, empty `catch {}`, ignored error returns in Go)?
- Do error responses leak stack traces, SQL fragments, file paths, versions or internal hostnames?
- What happens when the auth service, database or feature-flag service is unreachable — open or shut?
- Are partial failures handled (half-written transaction, retry storm, poison message)?
- Are timeouts set on *every* outbound call?

**Controls:** fail closed by default · explicit handling with logging · generic client-facing errors
with a correlation ID · circuit breakers with a safe fallback · chaos-test the auth dependency.

## Fast sweep order

When time is short, check in this order — it maps to how real incidents happen:

1. **Secrets in the repo** (`viora scan --only SECRET`) — minutes to exploit, trivial to find.
2. **Access control on every state-changing and object-reading route** (A01).
3. **Injection at the sinks the scanner flagged** (A05).
4. **Authentication and session handling** (A07).
5. **Supply chain: lockfile, install scripts, CI permissions** (A03).
6. **Exposed configuration and missing headers** (A02).
7. **Everything else.**
